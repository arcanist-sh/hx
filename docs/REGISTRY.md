# arcanist.sh package registry: design

Status: implemented locally (Worker + hx client), not deployed.
Default public URL (configurable everywhere): `https://registry.arcanist.sh`.

The registry is a Haskell package repository for the arcanist.sh ecosystem
(hx + BHC). It runs on Cloudflare Workers, with D1 as the source of truth and R2
for blobs. Its most important property is that **plain `cabal` can consume it
as an additional repository**, with no hx involved. hx adds a JSON API on top
(search, publish, yank, owners, tokens, BHC-verification attestations).

## 1. Goals and non-goals

Goals

- cabal-install 3.10+ (tested with 3.16.1.0) resolves and builds packages from
  the registry via a `repository` stanza, with full hackage-security (TUF)
  verification.
- Publishing never rewrites large objects. The index is append-only, like
  Hackage's `01-index.tar`, and clients update it incrementally with HTTP
  `Range` requests.
- `hx publish --registry arcanist`, `hx search --registry arcanist`,
  `hx registry login|logout|token|add|list`.
- BHC verification surfaced per version, recorded as signed attestations.

Non-goals (for now)

- Mirroring Hackage, or a proxy that merges Hackage into this index. Users list
  both repositories in cabal; cabal merges them.
- Hosting Haddock docs (planned, section 10).
- Running builds inside the Worker. The Worker cannot run GHC or BHC.

## 2. Cabal interoperability

### What cabal needs

cabal-install knows three remote repository kinds (`Distribution.Client.Types.Repo`):

| kind | cabal stanza | files fetched |
|------|--------------|---------------|
| legacy (`RepoRemote`) | `secure: False` (or omitted) | `00-index.tar.gz`, `package/<pkgid>.tar.gz` |
| secure (`RepoSecure`) | `secure: True`, `root-keys:`, `key-threshold:` | `timestamp.json`, `snapshot.json`, `root.json`, `mirrors.json`, `01-index.tar.gz` / `01-index.tar` (incremental, `Range`), `package/<pkgid>.tar.gz` |
| local no-index | `file+noindex://` | n/a |

The legacy kind is the minimum: one gzipped tar of `.cabal` files plus the
tarballs. It provides no integrity beyond TLS, and every `cabal update`
downloads the whole index.

### Decision: implement hackage-security properly, serve the legacy path too

Hackage-security turned out to be small enough to do correctly in a Worker:

- Signatures are Ed25519 over the canonical JSON of the `signed` object
  (`Text.JSON.Canonical`: sorted keys, no whitespace, only `"` and `\`
  escaped, integers only). Workers support Ed25519 in WebCrypto.
- Key ids are `hex(sha256(canonical({"keytype":"ed25519","keyval":{"public":base64(pk)}})))`.
- Per-package `package.json` target files in the index carry **no**
  signatures. Hackage does the same: their integrity comes from the index hash
  in the signed snapshot, and the `targets` role has no keys.
- Only `timestamp.json` and `snapshot.json` must be signed online. `root.json`
  and `mirrors.json` are signed offline and uploaded as finished files.

The same index is also served as `00-index.tar.gz`, so `secure: False` works.
That is useful for debugging and for very old clients, but the documented
stanza is the secure one.

Key layout (generated by `scripts/tuf-keygen.mjs`, run offline):

| role | keys | threshold | where the private key lives |
|------|------|-----------|-----------------------------|
| root | 3 | 2 | offline (owner's machine / hardware) |
| mirrors | 1 | 1 | offline |
| targets | 0 | 1 | unused (same as Hackage) |
| snapshot + timestamp | 1 shared "online" key | 1 | Worker secret `TUF_ONLINE_KEY` (JWK) |

Expiry: `root.json` 1 year and `mirrors.json` 1 year (both re-signed offline).
`snapshot.json` 14 days, `timestamp.json` 3 days, re-signed by the Worker:
on every publish/yank, lazily on any read that finds less than a day of
validity left, and by a daily cron.

If the secret is absent, the Worker serves only the legacy files and returns 404
for the TUF metadata. `secure: True` clients then fail closed, with a clear
error.

What "adding TUF later" would have cost: nothing on the storage side, because
the index layout is already Hackage's `01-index` (with `package.json`
entries). Only the signing endpoints, key ceremony and config are TUF-specific.
That is why they could be built now.

### Index storage: append-only, incremental, no big rewrites

`01-index.tar` is a sequence of tar entries plus a 1024-byte zero trailer.
Every publish (or yank, which appends a `preferred-versions` entry) appends a
**chunk**, the tar bytes of 1 to 3 entries:

- `<name>/<ver>/package.json`: TUF targets, with sha256 and length of the
  tarball under the key `<repo>/package/<name>-<ver>.tar.gz`
- `<name>/<ver>/<name>.cabal`
- `<name>/preferred-versions` (only on yank or unyank)

Chunks live in D1 (`index_chunks`, `seq` primary key) with their tar offset,
their gzip offset, the raw tar bytes, and a gzip **member** compressing the
same bytes. Because gzip allows concatenated members (RFC 1952 section 2.2; the
Haskell `zlib` decodes all members), `01-index.tar.gz` is the concatenation of
all chunk members plus a constant member that encodes the trailer. Nothing is
ever recompressed.

Snapshot hashes would normally need a full rehash of both files per publish. We
avoid that with a **resumable SHA-256** (`src/sha256.ts`). Its 104-byte
midstate is stored in D1 (`index_state`), and each publish resumes it over just
the new bytes. The final hash is computed on a clone of the state with the
trailer appended.

Concurrency: the append is one D1 `batch()`, which is a transaction. It inserts
`seq = expected_seq + 1` (a primary key conflict means another publish won the
race) and updates `index_state` from the state it read. On conflict the publish
retries with fresh state (up to 5 times). This serializes appends without a
Durable Object.

Sealing: a cron job (and a size trigger) moves runs of D1 chunks into
immutable R2 **segments** (`index/segments/<n>.tar` and `.tar.gz`, about
1 MiB+) and deletes the rows. D1 keeps a small tail, and R2 holds the bulk.
Serving `01-index.tar` streams segments in order, then the D1 tail, then the
trailer. A `Range` request touches only the overlapping segments (with R2
range reads) and chunks. No object is ever rewritten. Sealing a run writes
new objects and then repoints rows inside one D1 batch. Readers see either
the rows or the segment, never neither, because segments are written to R2
before rows are deleted.

Package tarballs are stored once at `packages/<name>-<ver>.tar.gz` in R2 and
are immutable (no overwrite, ever; section 6).

Yanking for cabal: Hackage-style. We append `<name>/preferred-versions`
containing `name <range excluding yanked versions>` (for example
`foo <1.2.0 || >1.2.0`). cabal treats it as a strong preference, so it avoids
yanked versions unless they are pinned (an existing `cabal.project.freeze`
keeps building, like crates.io). The tarball stays downloadable.

### Cabal stanza (written by `hx registry add`)

```cabal
repository registry.arcanist.sh
  url: https://registry.arcanist.sh/
  secure: True
  root-keys: <keyid1>
       <keyid2>
       <keyid3>
  key-threshold: 2
```

The root key ids are public. `GET /api/v1/config` returns them (along with the
threshold), and `hx registry add` fetches them from there. That endpoint is
trust-on-first-use. Users who want to pin can copy the ids from this README or
the arcanist.sh website. Pinned keys mean a compromised Worker cannot forge a
new root: cabal verifies root rotations against the old root's threshold.

## 3. JSON API (`/api/v1`)

Every response is JSON. Errors have the shape `{"error": {"code", "message", "hint"?}}`.

| method | path | auth | purpose |
|--------|------|------|---------|
| GET | `/api/v1/config` | none | registry name, URL, TUF root key ids and threshold, limits |
| GET | `/api/v1/search?q=&limit=` | none | name/synopsis search (prefix and substring ranking) |
| GET | `/api/v1/packages/:name` | none | versions (with yanked flag, published time, sha256), owners, latest, synopsis |
| GET | `/api/v1/packages/:name/:version` | none | metadata, `build-depends`, cabal file URL, tarball URL, attestations |
| PUT | `/api/v1/packages/upload` | token (publish) | body = sdist `.tar.gz` (`application/gzip`) |
| PUT/DELETE | `/api/v1/packages/:name/:version/yank` | token (yank) | yank / unyank |
| GET | `/api/v1/packages/:name/owners` | none | list owners |
| PUT/DELETE | `/api/v1/packages/:name/owners/:login` | token (owners) | add / remove owner (the last owner cannot be removed) |
| POST | `/api/v1/packages/:name/:version/attestations` | verifier signature | record a BHC verification |
| GET | `/api/v1/tokens` · POST · DELETE `/:id` | token | list, create, revoke your tokens |
| GET | `/api/v1/me` | token | who am I, token scopes |
| POST | `/api/v1/admin/users` | admin | create a user and their first token |
| POST | `/api/v1/admin/users/:login/tokens` | admin | recovery token for an existing user |
| POST | `/api/v1/admin/verifiers` | admin | register a verifier public key |
| PUT | `/api/v1/admin/reservations/:name` | admin | grant a reserved name to a user |
| PUT | `/api/v1/admin/tuf/:file` | admin | upload offline-signed `root.json` / `mirrors.json` |

Repository (cabal) paths: `/01-index.tar`, `/01-index.tar.gz`,
`/00-index.tar.gz`, `/timestamp.json`, `/snapshot.json`, `/root.json`,
`/mirrors.json`, `/package/<pkgid>.tar.gz`, plus convenience
`/package/<pkgid>/<name>.cabal`.

### Publish validation (server side, before anything is stored)

1. `Content-Length` must be present and no larger than 16 MiB. The body is read
   with a counting limit, so a lying header does not help.
2. gzip decompression is streamed with a 64 MiB cap (zip-bomb guard).
3. The tar is parsed (ustar, GNU long names, pax). Only regular files and
   directories are accepted; symlinks, hardlinks and devices are rejected. Every
   path must start with `<name>-<ver>/`, and no path may be absolute or contain
   `..`, backslashes or NUL. The tar may hold at most 10,000 entries.
4. `<name>-<ver>/<name>.cabal` must exist (at most 1 MiB). Its top-level `name:`
   and `version:` fields are parsed and must match the tarball's top directory.
5. The name must match cabal's grammar (`[A-Za-z0-9]+` words joined by `-`,
   each word containing a letter), and the version must be dotted numerals.
6. The name policy is checked (section 6). The version must not exist already,
   yanked or not.
7. The sha256 is computed, the tarball goes to R2, rows go to D1, and the index
   chunk is appended.

Extracted `build-depends` (best effort: union over all components, package
name and range text) are stored for the API. cabal reads the real `.cabal`
file anyway.

## 4. Authentication

- **API tokens**: `hxr_` + 32 random bytes (base64url, from
  `crypto.getRandomValues`). A token is shown once. D1 stores only the
  SHA-256 of the token. A fast hash is fine at 256 bits of entropy, and it
  makes lookups O(1). Each token has a name, scopes (`publish`, `yank`,
  `owners`, `tokens`), an optional package allow-list, an optional expiry and a
  `last_used_at`. Tokens are revocable.
- **Bootstrap/admin**: the secret `ADMIN_TOKEN`, compared in constant time
  (`crypto.subtle.timingSafeEqual` over SHA-256 digests). The admin creates
  users (`POST /admin/users`), and each user receives a first token. There
  is no web login yet. GitHub OAuth login is follow-up work.
- **Ownership**: the first publish of a name makes the publishing user its
  owner. Later publishes, yanks and owner changes require ownership (and the
  scope, and the package being in the token's allow-list if it has one).
- **Trusted publishing (follow-up)**: GitHub Actions OIDC. A package owner
  registers `(repository, workflow, environment)`. The workflow posts its OIDC
  JWT to `/api/v1/oidc/exchange`. The Worker verifies RS256 against GitHub's
  JWKS (`token.actions.githubusercontent.com`), checks `aud`, `iss`,
  `repository`, `job_workflow_ref` and expiry, and mints a 15-minute token
  scoped to that package. The data model is easy to add (`trusted_publishers`
  table). It is not implemented, because it cannot be end-to-end tested
  without GitHub.

## 5. BHC-verified packages

The Worker cannot run BHC. Verification is therefore an **attestation**, a
statement signed by a registered verifier (a CI job):

```json
{
  "package": "foo", "version": "1.0.0",
  "sha256": "<sha256 of the exact tarball>",
  "bhc_version": "0.2.17", "profile": "default",
  "result": "pass",              // pass | fail
  "log_url": "https://github.com/.../actions/runs/123",
  "built_at": "2026-10-19T12:00:00Z"
}
```

The verifier signs the canonical JSON of that object with its Ed25519 key and
POSTs `{ "attestation": {...}, "verifier": "<name>", "signature": "<base64>" }`.
The Worker:

- looks up the verifier's public key (admin-registered, revocable),
- verifies the signature,
- checks `sha256` against the stored tarball, so an attestation cannot be
  replayed onto a different upload.

The attestation is stored (one row per verifier, version, bhc_version and
profile, replaceable by the same verifier). The package version API shows
`attestations[]` and a derived `bhc_verified` (a passing attestation exists for
that version).

`verifier/bhc-verify.yml` is a documented GitHub Actions workflow. It is
triggered by `repository_dispatch` or a schedule, polls
`/api/v1/unverified`, builds each tarball with BHC per profile, signs with
the key from secret `BHC_VERIFIER_KEY` using `scripts/attest.mjs`, and posts
the result.

## 6. Abuse and safety

- **Rate limits** (Workers Rate Limiting binding): `PUBLISH_LIMITER` allows 10
  per minute per user, `AUTH_LIMITER` allows 30 per minute per IP for
  token-bearing requests (so token guessing is throttled), and
  `ATTEST_LIMITER` allows 60 per minute per verifier. Reads are cached at the
  edge (`Cache-Control`) and fall under Cloudflare's normal DDoS protection.
- **Sizes**: tarball at most 16 MiB, unpacked at most 64 MiB, at most 10,000
  entries, `.cabal` at most 1 MiB, attestation body at most 16 KiB.
- **Immutability**: `(name, version)` can never be re-uploaded, not even after
  a yank, and package deletion does not exist. This matches Hackage and
  crates.io, and it is what makes the TUF hashes meaningful.
- **Name squatting and confusion**: cabal **merges** packages with the same
  name across repositories. A registry package named `aeson` would therefore
  inject versions into every user's `aeson` solve. So:
  - names that exist on Hackage are **reserved**. On first publish of a new
    name the Worker asks Hackage (`GET hackage.haskell.org/package/<name>/preferred`
    with `Accept: application/json`) and caches the answer in D1. A 200 rejects
    the publish with a hint. If Hackage is unreachable the publish fails
    closed. An admin can grant a reserved name to a user (for example the
    Hackage maintainer, who wants a BHC-verified mirror).
  - names are unique **case-insensitively** (`Foo` vs `foo`), and `_`/`-`
    are not interchangeable in cabal anyway.
  - a small built-in deny list covers GHC boot and wired-in packages (`base`,
    `ghc-prim`, `ghc`, `rts`, `integer-gmp`, `template-haskell`, and others).
- **Tarball safety**: see the validation list in section 3. Downloads are
  served with `Content-Type: application/gzip`,
  `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.
  No uploaded content is ever served as HTML.
- **Secrets**: `ADMIN_TOKEN` and `TUF_ONLINE_KEY` are Worker secrets only, and
  `.dev.vars` is git-ignored.

## 7. Data model (D1)

See `migrations/0001_init.sql`. Tables: `users`, `tokens`, `packages`
(`name` PK, `name_lower` UNIQUE, synopsis, created), `package_owners`,
`versions` (name, version, sha256, size, cabal text, deps JSON, yanked,
published_by, published_at), `index_chunks`, `index_segments`, `index_state`,
`tuf_meta` (current signed snapshot/timestamp bytes and versions),
`verifiers`, `attestations`, `name_reservations` (Hackage lookup cache plus
admin grants), and `audit_log` (publish, yank, owner and token events).

## 8. hx client

- `hx.toml` (project) and the global `config.toml` gain `[registries.<name>]`
  with `url = "..."`. The built-in `arcanist` entry points at
  `https://registry.arcanist.sh`, and both config files can override it.
  **Hackage stays the default** for `publish` and `search`: the registry is
  opt-in via `--registry <name|url>` until it is live.
- Credentials live in `<hx config dir>/credentials.toml` with mode 0600 on Unix,
  keyed by registry URL. No keychain crate is in the tree, and we did not add
  one. `HX_REGISTRY_TOKEN` overrides the file (for CI).
- `hx registry login [--registry] [--token-stdin]`, `logout`, `list`,
  `token create|list|revoke`, `add` (writes the `repository` stanza into
  `cabal.project`, fetching root key ids from `/api/v1/config`, and creating
  `cabal.project` with `packages: ./*.cabal` if absent). The repository is
  named after the URL's host, so production and a local dev server keep
  separate cabal caches.
- `hx publish --registry X`: the same pre-publish checks, then `cabal sdist`,
  then an upload to `PUT /api/v1/packages/upload`.
- `hx search --registry X` uses the JSON search API.

## 9. Cost (Cloudflare, list prices as of 2026)

See README "Cost estimate". In summary, a small-to-medium registry (thousands
of packages, about 1M index/package downloads per month) fits in the **Workers
Free** plan except for the cron triggers and rate-limiting binding (both
available on Free), and costs about $5 per month on **Workers Paid**. R2 egress
is free, and the dominant cost driver is R2 Class B reads beyond 10M per month.

## 10. Follow-ups

1. GitHub OIDC trusted publishing (section 4).
2. GitHub OAuth web login, plus a minimal HTML frontend (package pages).
3. Haddock docs hosting: `PUT /api/v1/packages/:name/:version/docs` (a docs
   tarball to R2 under `docs/<pkgid>/`), served from a separate origin
   (`docs.registry.arcanist.sh`) so user HTML never shares the API's origin.
4. `hx add` resolving registry-first with Hackage fallback. Once the stanza
   is in `cabal.project` cabal already does this. hx's own solver would need
   to read this registry's index.
5. Root-key rotation tooling (sign a new `root.json` with the old threshold).
6. Metadata revisions (`.cabal` x-revision), which Hackage supports and which
   append a new `.cabal` entry. The index design already allows this.
